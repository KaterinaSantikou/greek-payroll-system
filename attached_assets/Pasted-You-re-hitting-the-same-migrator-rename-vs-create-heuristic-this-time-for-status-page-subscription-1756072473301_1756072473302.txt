You’re hitting the same migrator “rename vs create” heuristic—this time for status_page_subscriptions. The safe fix is to pre-create the exact table (idempotently) so the tool stops offering to rename partners.

Do this once (SQL — Postgres/Supabase)

Run in your SQL editor or as a migration file.

create extension if not exists pgcrypto;

-- Generic helper to avoid rename prompts
create or replace function public.ensure_table(p_table text, p_sql text)
returns void language plpgsql as $$
begin
  if not exists (
    select 1 from information_schema.tables
    where table_schema='public' and table_name=p_table
  ) then
    execute p_sql;
  end if;
end $$;

-- Create the subscriptions table if missing
select public.ensure_table(
  'status_page_subscriptions',
  $SQL$
  create table public.status_page_subscriptions (
    id uuid primary key default gen_random_uuid(),
    email text not null,
    component_slug text,               -- subscribe to specific component (nullable = all)
    is_verified boolean not null default false,
    verify_token uuid default gen_random_uuid(),
    created_at timestamptz not null default now(),
    verified_at timestamptz,
    unsubscribed_at timestamptz
  );

  create unique index if not exists uniq_status_subscriptions_email_component
    on public.status_page_subscriptions (lower(email), coalesce(component_slug,''));

  create index if not exists idx_status_subscriptions_created_at
    on public.status_page_subscriptions (created_at desc);
  $SQL$
);


Then re-run deploy and, in the dialog, choose:

❌ Do not rename/move partners

Why it keeps suggesting partners → status_page_subscriptions

Your migrator sees a table expected by code that doesn’t exist and tries to be “helpful” by proposing renames from existing tables. Because partners happens to be present, it’s offered as a candidate. By ensuring the correct table already exists, the rename option disappears.
