still land on a frontend 404 after Sign In. That’s almost always a frontend ↔ backend handoff issue:

SPA is rendering its own “404” view because it thinks you’re not logged in.

Why it “thinks” that: the SPA’s API calls are hitting the wrong origin (localhost vs replit.dev), or it’s not sending cookies (credentials:'include'), or CORS isn’t allowing credentials, or you’re redirecting to a different subdomain than the one setting the cookie.

Use the commands below (copy/paste exactly) to make your agent prove which one it is and then apply the smallest fix.

Phase 1 — Prove what the SPA is calling and whether cookies are sent
FE-Network-Probe (read-only)
1) In the browser console on the 404 page:
   console.log('origin:', window.location.origin)

2) Still in console, hit whoami on the SAME origin (no hardcoded host):
   fetch('/api/whoami', { credentials: 'include' })
     .then(r => r.json()).then(console.log).catch(console.error)

3) Open DevTools → Network → filter by 'whoami' or your initial bootstrap API (e.g., /api/me):
   - Copy Request URL, Status, and the Request Headers:
     • :authority / Host
     • Origin
     • Cookie (should be present if same-origin)
   - Copy Response Headers:
     • Set-Cookie (if any)
     • Access-Control-Allow-Origin / Credentials (if present)

4) In the SPA codebase:
   - grep -RIn "axios.create" "baseURL" "fetch(" src frontend app
   - Print any absolute base URLs (e.g., http://localhost:5000 or https://<other-domain>)


Interpretation

If Request URL points to http://localhost:5xxx
 (or a different domain) → you’re cross-origin.

If Request URL is same origin but no Cookie header → fetch isn’t using credentials:'include'.

If it’s cross-origin and there is no Access-Control-Allow-Credentials: true → browser drops cookies.

Phase 2 — Verify the cookie domain + redirect host match
Cookie-Domain-Host-Check (read-only)
1) From the /oauth2callback 302 response, print the exact Set-Cookie line again.
2) Log on the server (one-liner in /oauth2callback handler before redirect):
   console.log('[AUTH][cb] redirecting to host:', req.get('x-forwarded-host') || req.get('host'));
3) In the browser console after redirect, print:
   console.log('landed on:', window.location.origin)
4) Confirm: cookie domain (implicit host) === landed host. If they differ (e.g., deployment vs workspace subdomain), the cookie won’t be sent.

Phase 3 — Check route order (make sure SPA catch-all doesn’t shadow debug)
Routes-Order-Check (read-only)
1) curl -i "https://<REPLIT_DOMAIN>/__auth_ok" -H "X-Forwarded-Host: <REPLIT_DOMAIN>" | head -n1
   - Should return our text, not the SPA. If SPA responds, the catch-all is above our routes.
2) Print where app.use(express.static(...)) or app.get('*', ...) is mounted; it must be AFTER auth and debug routes.

Phase 4 — Apply the minimal fix (pick the matching scenario)
Scenario A — Frontend calls the wrong origin (e.g., localhost)
ApplyFix:FE-BaseURL
- Change the SPA API base to relative paths ('/api/...') or to the exact HTTPS Replit domain.
- For axios: axios.create({ baseURL: '' /* relative */ , withCredentials: true })
- For fetch: always use fetch('/api/...', { credentials: 'include' })
- Remove hard-coded http://localhost:5000.
Show unified diff only (do not auto-apply without approval).

Scenario B — Frontend not sending cookies
ApplyFix:FE-Credentials
- For every initial bootstrap/API call (whoami, me, session):
  fetch('/api/whoami', { credentials: 'include' })
  // or
  axios.get('/api/whoami', { withCredentials: true })

- Ensure the app-wide axios instance has withCredentials: true.
Show unified diff only.

Scenario C — Cross-origin needed (different FE/BE origins)
ApplyFix:CORS-Credentials
Server:
  import cors from 'cors';
  app.use(cors({
    origin: ['https://<REPLIT_DOMAIN>'],  // exact origin(s)
    credentials: true,
    methods: ['GET','POST','PUT','PATCH','DELETE','OPTIONS'],
    allowedHeaders: ['Content-Type','Authorization']
  }));
  app.set('trust proxy', 1);

Client:
  axios/fetch calls: withCredentials: true / credentials: 'include'

- Verify response headers include:
  Access-Control-Allow-Origin: https://<REPLIT_DOMAIN>
  Access-Control-Allow-Credentials: true
Show unified diff only.

Scenario D — Cookie set on one host, redirect to another host
ApplyFix:Callback-Host-Consistency
- Ensure CALLBACK = `https://${REPLIT_DOMAINS.split(',')[0]}/oauth2callback`
- Ensure the final redirect after passport.authenticate points to the SAME host (no hard-coded other domain).
- If using a deployment domain, use that exact domain consistently for both Set-Cookie and post-auth redirect.
Show diff only.

Scenario E — SPA “404” view because /dashboard route path mismatch
ApplyFix:Dashboard-Route
- If SPA’s route is '/app/dashboard' (or similar), change successReturnToOrRedirect to that path.
- Or add a server redirect from '/dashboard' -> '/app/dashboard'.
Show diff only.

Phase 5 — Prove the fix worked
Post-Fix-Proof
1) In browser console:
   fetch('/api/whoami', { credentials: 'include' }).then(r=>r.json()).then(console.log)
   # Expect: { authenticated: true, user: {...} }

2) Reload the SPA; it should render the authenticated dashboard (no 404).

3) DevTools Network:
   - Verify API calls are to the correct origin
   - Verify Request Headers include Cookie on same-origin, or include credentials if cross-origin

Quick sanity checklist (keep)

 SPA uses relative API URLs (or the exact same origin)

 All SPA API calls send credentials (withCredentials: true / credentials: 'include')

 If cross-origin, server CORS is set with specific origin and credentials:true

 Callback host matches the SPA host that renders /dashboard

 SPA has a real /dashboard route (or adjust success redirect to existing route)
