backend code expects a unified table called status_page_incidents (likely for a Status Page / Incident log). Your database already has earlier/parallel schemas:

system_outages – historic outage records

system_status_checks – uptime/health pings

partners – unrelated CRM-ish table (do not touch)

The migrator asks whether to create a new table or rename/move one of the existing tables into status_page_incidents.

The safe choices (pick one)
✅ Option A — Create fresh table (recommended now)

Use this if:

You introduced a new Incident model and don’t need to merge legacy data immediately.

You want to deploy fast and migrate data later.

In the dialog choose:
Create new status_page_incidents table
Do not rename partners, system_outages, or system_status_checks.

This avoids collateral damage (especially renaming partners which is unrelated).

✅ Option B — Merge legacy outages into the new table (if you want continuity)

Use this if:

status_page_incidents replaces system_outages (and possibly summarizes failed system_status_checks into incidents).

In the dialog choose:
Create new status_page_incidents table (first), then run a one-time migration to copy historical data from system_outages into it. Keep system_status_checks as-is (it’s a feed for uptime, not incidents).

Avoid “Rename/move partners → status_page_incidents”. That would break anything relying on partners.

Concrete migration you can run (Postgres / Supabase)

Create the new unified table (idempotent & future-proof):

create extension if not exists pgcrypto; -- for gen_random_uuid()

create table if not exists public.status_page_incidents (
  id uuid primary key default gen_random_uuid(),
  title text not null,
  description text,
  severity text not null default 'info' check (severity in ('info','minor','major','critical')),
  status text not null default 'investigating' check (status in ('investigating','identified','monitoring','resolved')),
  started_at timestamptz not null default now(),
  resolved_at timestamptz,
  created_by uuid, -- optional FK to users table if you have one
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index if not exists idx_status_page_incidents_started_at on public.status_page_incidents(started_at desc);

create or replace function public.tg_status_page_incidents_updated_at()
returns trigger language plpgsql as $$
begin
  new.updated_at := now();
  return new;
end $$;

drop trigger if exists tr_status_page_incidents_updated_at on public.status_page_incidents;
create trigger tr_status_page_incidents_updated_at
before update on public.status_page_incidents
for each row execute function public.tg_status_page_incidents_updated_at();


(Optional) Copy historic outages into the new table:

Adjust the column names if they differ in your system_outages.

insert into public.status_page_incidents
  (id, title, description, severity, status, started_at, resolved_at, created_at, updated_at)
select
  coalesce(so.id, gen_random_uuid()) as id,
  so.title,
  coalesce(so.details, so.description) as description,
  case lower(so.impact)
    when 'high' then 'critical'
    when 'medium' then 'major'
    when 'low' then 'minor'
    else 'info'
  end as severity,
  case
    when so.ended_at is null then 'resolved' -- flip if your semantics are different
    else 'resolved'
  end as status,
  so.started_at,
  so.ended_at as resolved_at,
  now(), now()
from public.system_outages so
where not exists (
  select 1 from public.status_page_incidents spi
  where spi.id = so.id
);


Keep public.system_status_checks as-is. It’s typically a high-frequency table for pings. If you later want automatic incident creation from consecutive failures, do that in app logic or a cron job that writes into status_page_incidents.

(Optional) Deprecation guard
If your code still references old tables in places, create views temporarily:

create or replace view public.v_system_outages as
select * from public.status_page_incidents;


(Only do this if you absolutely need a stopgap while refactoring queries.)

Why your dialog shows those rename options

Most migration frameworks (Prisma/Drizzle/Knex migrations, or Supabase diff) detect table-name collisions and offer rename paths. Because status_page_incidents is new, and partners/system_outages/system_status_checks already exist, the tool guesses you might be consolidating. We’re explicitly choosing the non-destructive path (create new table) and migrating data intentionally rather than renaming unrelated tables.
